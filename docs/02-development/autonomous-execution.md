# 自主執行與收斂規範

版本：1.0｜文件日期：2026-10-17（Asia/Taipei）
建議位置：`docs/02-development/autonomous-execution.md`
生效條件：維護者明確採用本規範，並另行指定當次實作／工具操作範圍。

> 本規範決定「如何做完已授權工作」，不增加產品需求，不取代核准計劃、驗收 catalog、真站／刪除／發布核准，也不是新的 runtime 或 CI framework。

## 0. 一分鐘執行摘要

1. 從核准計劃選下一個前置成立的工作；不要因使用者暫時不在就改做自己想到的專案。
2. 每個切片先寫可觀察的完成條件，直接引用既有案例；不重寫整份計劃。
3. 有具體失敗及首因，且修正不改需求、信任邊界或授權，就自主小修，不逐次請示。
4. 多個失敗共用首因，修一條完整相關路徑；不要每個症狀各補一個例外。
5. 跨責任、驗收目標不同或回饋太慢時才切片；只有一個根因的小修不強迫切片。
6. 同根因連續兩次沒有新證據，不直接做第三次猜測：先做一次有限的診斷重置。
7. 重置仍無進展，封存該阻擋並轉做前置已成立的獨立工作；不無限研究或悄悄放寬門檻。
8. 必要驗證與覆核通過就結案並自動接續下一個已授權工作，不為追求完美重開已完成設計。
9. 工具權限、實作完成、測試通過、獨立覆核、階段出站、真站與發布核准分開記錄。
10. 只維持一份精簡工作狀態；不為管理自己新增 checker、registry、事件系統或無限代理排程器。

## 1. 權威、授權與一次性指示

核准計劃及 catalog 定義應交付的行為與階段門檻；本規範只管理執行方法。維護者的當次授權決定可改 repository／branch、工具操作、費用及外部副作用。工具的實際 sandbox／approval 限制另外成立，不能用文件繞過。

舊對話中的「這輪只修某案例」「本輪只准一次重跑」「完成切片就停止」是針對當輪的操作限制。只有維護者明確宣布改採連續授權後，才以新的連續授權取代這些已完成切片的限制；不得自行忽略仍有效的限制。

採用本規範時，同步移除或改寫 `AGENTS.md`、測試執行指南等文件中直接衝突的工作節奏條款。保留驗證內容與結果可信度要求。不得同時留下「階段只能跑一次 CI」和「有證據可重跑」而讓後續代理自行猜測優先序。

連續授權可以包含相依階段內的自主實作、測試、checkpoint 與限定分支 push，但不能自動推得真站連線、使用私人資料、P6c 最終 legacy 刪除或正式發布已核准。需求／catalog／權限政策的變更須分開取得維護者決策。

## 2. 每次恢復工作的最小核對

讀取當前 `AGENTS.md`、本規範、已採用計劃的當前階段、必要的 catalog 條目，以及上一份工作狀態。核對 repository、branch、HEAD、工作樹與正在執行的工作。不要每次重新讀全倉庫或重新核准完整 catalog。

記錄只描述可核對的事實：適用授權、核准 digest、實際 candidate、已完成 gate、待補覆核、既有 CI run／attempt。工作狀態不是結果的權威，仍要對照實際檔案與原始證據；但不需毫無原因地重放所有已驗證測試。

正在進行的實作由單一主代理持有寫入權。新訊息、文件採用與 review 工作在安全檢查點併入，不與另一個仍在修改相同檔案的 session 同時寫入。不要為讀取新規範粗暴中止在途測試或丟棄修改。

## 3. 自主決策表

| 情況 | 自主行動 | 何時才升級／停止 |
|---|---|---|
| 已知錯誤，根因及最小修法清楚 | 修直接相關路徑，跑原失敗與受影響回歸 | 需要改核准契約或操作權限 |
| 多個失敗指向共用 helper／fixture | 按最早失敗分群，一次修共同根因 | 無法辨識因果則做有限診斷，不逐測試打補丁 |
| 需求內新功能，存在不同可獨立驗收責任 | 拆少數垂直切片，先完成最小完整路徑 | 切片切斷必要原子提交／打包單位時不可拆 |
| 新反例確實違反已核准 invariant | 補回歸並修正，即使未列成獨立 case 也不忽略 | 必須改正式義務集合／政策時提出規格決策 |
| 只是想到更強的敵對模型或通用性 | 記入非阻擋建議，不加入本階段必做 | 只有維護者另核准才納入 |
| 跨 OS／artifact／打包接合問題 | 在既有授權環境重現，修最小邊界並測真實傳遞 | 需新平台、費用、管理員權限或秘密資料 |
| 所需 catalog 內容與核准 digest 未變 | 沿用既有內容核准；對新程式碼做差異覆核 | 規格語意、位元組或核准來源改變 |
| 高風險覆核缺席／額度耗盡 | 保留固定候選，做不依賴其出站的同階段獨立工作 | 不得自審冒充獨立覆核或通過受阻階段 |
| 所有已到期門檻真正通過 | 記錄完成，自動接下一個已授權且前置成立的工作 | 不再新增風格性工作阻擋結案 |
| 真站、最終刪除或發布核准缺失 | 保留對應 BLOCKED，執行明確不依賴該 gate 的允許準備 | 不自行採用新政策解除阻擋 |

「小修」以是否保持既有契約及變更責任集中判定，不以五行、五個檔案或單一 commit 判定。必要修正可能跨 launcher、validator、fixture 與測試；只改其中一個造成條件不一致，不算較簡潔。

## 4. 每個切片只需一張短工作卡

在現有工作狀態寫下以下內容即可，不另外建立一套規格檔：

- 目標與來源：哪個階段、哪些既有 obligation／invariant。
- 最小交付：使用者或測試可觀察到什麼結果。
- 修改邊界：主要責任、必要直接依賴；本片明確不做什麼。
- 驗收：合法對照、指定負向因果、相關真實環境／打包要求。
- 停止條件：哪些是完成，哪些需要外部決策。

未知的內部實作細節由代理選擇最小且可驗證的做法。不要求所有底層欄位都由人類先決定，也不以「完整矩陣未達理想」拖延第一個可驗收路徑。

沒有需求／驗收邊界變更時，函式拆分、私有 helper、fixture 格式的小改動可自主處理；要同步修正直接相關 caller 和測試。超出計劃已核准範圍的公開 API、正式 evidence schema、required catalog 或外部相容性承諾變更，不屬於自由調整。計劃明訂的新增型別、介面與破壞式變更可依原授權實作，不因出現新 API 名稱就再要求人類決策。

## 5. 何時切片、何時不要切片

適合切片：一項工作同時包含型別／純規則、I/O 接合、資源打包、狀態轉移等不同驗收責任；或一次改太多導致無法從失敗定位根因。優先沿著可觀察行為切出約二至四個工作單位，數量不是 gate。

先形成「一份合法輸入 → 實際核心處理 → 可核對輸出 → 一個相關錯誤」的完整路徑，再推展同類案例。不要先完成所有抽象、所有介面、所有 fixture，最後才驗第一條真實路徑。

不適合切片：一個來源條件與 launcher 不一致的小 bug；同一次 guard＋commit 的原子操作；計劃明訂同一合併單位完成的 source／JS resources／loader／spec／frozen 自測。切片是降低回饋成本，不是分割必要的一致性。

切片完成但 phase 尚有其他前置成立工作：主動接續。只有維護者仍指定逐片核准時才停下等人。

## 6. 失敗處理：按首因，不按測試數

對每個失敗先分清楚：建置／fixture 未成立、工具未啟動、程式真的執行且違反契約、結果收集錯誤、環境／權限不足。缺 report 常是下游症狀；不要先補空 report、改預期文字或忽略例外。

一次大量失敗先分成少數首因群。選代表案例追蹤完整直接鏈路，再修共用根因。修完代表案例及合法對照後，再跑整群。不能在沒有因果依據時宣稱其他失敗全部同根因。

每個負向測試先有合法正向對照；只改宣告的輸入差異，驗證指定原因、指定對象及必要階段。其他無關前置失敗不算達成。前置拒絕只有在它就是該案例要求的行為時才成立。

測試資料可共用格式工具，但預期結果不能直接呼叫被測接受邏輯來證明自己。不同 OS、source／frozen、producer／artifact／aggregate、正常路徑／恢復路徑分開驗證；不能用其中一層的成功代替另一層。

修跨環境缺陷時，至少覆蓋實際失敗邊界，例如 artifact mode 正規化、Windows 路徑序列化、frozen 任意 cwd。這不是要求對每個小改動重建全部環境。

## 7. 反覆嘗試的收斂控制

### 7.1 什麼才算新證據

新證據包括：更小的可重現輸入、找到更早的實際失敗點、排除一個根因假設、讓原本沒執行到的指定檢查真正執行、代表案例由失敗變通過、測到先前缺少的平台行為。

新增欄位、更多 digest、更多程式行、改了錯誤字串、換 reviewer、改變症狀但沒有逼近既有驗收，不能單獨當成進展。

### 7.2 兩次無進展先診斷，不立即放棄或再猜

同一根因連續兩次修補仍停在相同首因且沒有新證據，暫停擴寫，做一次有限的診斷重置：

1. 保留目前可恢復候選與失敗結果。
2. 重讀既有驗收，追查直接完整路徑，建立最小重現。
3. 最多比較兩個針對該根因的修法，選擇最小且可驗證的一個。
4. 只做一輪針對性驗證，再決定是否恢復正常切片。

若獲得新證據、且契約與授權未變，可繼續小修；「第三次」不是自動禁止。若重置仍沒有可驗證進展，或又要擴大信任模型／通用 schema，將該工作標為 `BLOCKED_ANALYSIS`／`AWAITING_DECISION`，不要再以換名字、換 agent 或新分支清零次數。

### 7.3 阻擋局部化

被阻擋的是具體工作及其依賴，不是必然整個 session。可繼續同階段內前置已成立、在授權範圍且不破壞固定候選的獨立工作。跨階段只有原計劃允許的獨立準備可以先做；不得跳過 phase 出站而宣稱後續階段完成。

同一環境／權限阻擋沒有新輸入時不反覆探測。依賴循環或真正需要維護者決策時，用簡短紀錄列：已知事實、最小重現、兩個方案的取捨、所需核准。不可自行選擇削弱產品要求的方案。

## 8. 防範自動擴張與過度設計

新增一項檢查／抽象／工具前，先能說明：違反哪個已核准要求、目前哪個反例會出錯、既有機制為什麼不能處理、最小替代方案是什麼。無法回答就不放入當期關鍵路徑。

保留已知信任模型的終點。Checksum 驗位元組一致，不等於核准身分、實際使用或指定失敗原因。不能為了 candidate 可同步改所有資料與程式的假設，持續增加自我證明層。

新增回歸以保護既有 invariant，不等於新增 required catalog 規格；新增／刪減／延後正式義務、降低層級或擴大不適用條件，仍要維護者決策。不要為了避免 catalog 變更而放任具體 bug，也不要把每個測試 helper 都升級成規格。

沒有具體收益，不引入通用事件匯流排、DI 容器、第二套引擎、第二份業務規則、泛用 verifier framework 或 agent orchestrator。已通過且與當前問題無關的設計不重開。

發現低風險、未違反當期要求的命名或風格問題，記入現有後續清單；同位置順手修正只有在極小、可驗證且不擴大回歸範圍時才做。真正必要的簡潔度工作不能用「後續」無限拖延，但也不能把所有美化變成 phase blocker。

## 9. 測試、CI 與 build：按用途，不設僵硬次數

採三層節奏：原失敗／精確 node → 受影響 family → 固定候選的階段完整驗收。共用 helper 變動就納入所有受影響 family；無變更不重跑只為心理安心。

語法 gate 涵蓋當期核准 base→candidate 及適用工作樹範圍，不能只編譯固定目錄或未暫存 diff。Typecheck、pytest、browser、frozen、真站各有責任，不能互相冒充。

CI 分為診斷與正式出站：本機可快速定位者先本機；只有遠端才具備的 OS／隔離／build 條件，可在既有授權內用定向診斷 job。每次遠端重跑都要對應新修正、新環境證據或有根據的暫時故障，不原封不動重跑碰運氣。

不設「每 phase 只能一次 CI」或「最多一個 commit」。需要乾淨 HEAD 才能測試時，允許符合授權的 checkpoint commit；明記 `REVIEW_PENDING`／`VALIDATION_PENDING`，不得把 checkpoint 當作已合併或已驗收。

正式候選實作與必要覆核穩定後，完成所有已到期 gate；失敗則局部修正、差異覆核及必要重驗。正式多 job 彙總遵循同 SHA／run／attempt 與既有證據繼承契約，不拼接舊結果。已通過的較早候選保留歷史證據，不自動變成新 SHA 的成功。

Import、依賴、resources、spec 變更仍執行原計劃要求的產品打包／frozen 驗證；本機無目標 OS 時使用已授權、可用的原生目標 runner，不用 Linux 結果冒充。P3a 同期打包不能延到 P8。

測試 image 準備與產品打包都需當次授權；下載／安裝依賴在隔離測試開始前完成。執行 browser／driver／子程序的硬隔離不因工作時長而降低。

## 10. 固定候選覆核與結案

主代理負責整合及寫入。高風險變更由真正獨立 reviewer 覆核；最多同時兩位，分工互補，不遞迴派發。Reviewer 的任務是找具體契約缺陷，不是產生更多抽象建議。

受審查範圍固定到 SHA 或明確的完整工作樹快照；審查期間不改該範圍。收齊 findings、合併同根因後再修。已通過且內容與依賴未變的 review 可沿用，新修改只覆核差異及直接影響路徑。全部變更要有覆蓋說明，不等於每位 reviewer 都要逐字重讀所有文件與重複資料。

Finding 需有位置、觸發條件、實際後果與核准條款／既有 invariant。主代理可判定不成立的 finding，但要列反證；不能因 reviewer 名稱或人數自動把風格建議升級為 blocker。遇無法裁決的重大契約分歧，停止該項請示。

Reviewer 額度不足時保留待覆核狀態；可繼續同階段不依賴出站的工作，不因等待而建立第二套 review framework。已有符合規範的獨立覆核，就不反覆增加人次直到「人人同意」。

正式完成條件：已到期驗收均有合格證據、必要覆核完整、無未處理的必要缺陷、所需外部核准有效。成立即標 `VERIFIED`，給一次簡短進度後繼續下一個有權執行的工作。不能每次結案又追加一項「也許更好」來延長階段。

## 11. 持久工作狀態，不製造新的管理框架

沿用現有成果目錄的一份 Markdown 狀態檔；沒有才使用 `artifacts/utiki-ci/autonomous-status.md`。它不屬於正式 required catalog、source snapshot 或測試 PASS 的權威。按現有 artifact 管理規則保存，勿將測試原始碼藏進 ignore 規則。

切片完成、根因判斷改變、遇阻擋、階段出站及預計 context 切換時更新。只保留當前事實與近期必要決策，原始 logs 另以路徑引用。不寫逐 token 推理，不把規範內容再複製一次。

```text
授權：核准訊息／適用 repository、branch、可做及不可做操作
計劃／catalog：版本與核准來源；未變則沿用，不自行核准
當前 HEAD／dirty 狀態；已驗收的 exact candidate
目前 phase／切片；前置已通過／尚缺
本片完成條件及原 case／obligation 來源
已完成結果：命令、候選、run／attempt、原始證據路徑
待覆核：範圍、reviewer、既有 findings 處置
失敗首因：最小重現、已排除假設、上次新證據
無進展次數／診斷重置是否使用
阻擋：類型、責任人、解除所需輸入；不代填核准
下一個立即動作：一項具體任務，不是「繼續研究」
後續建議：與當期 gate 分開，不自動變成必做
```

不要為每次狀態更新建立 commit；否則會造成「記錄測試結果 → SHA 改變 → 又全套重測 → 再改紀錄」的循環。正式版本文件仍在適當的下一個可審查提交更新，清楚保留已測 SHA，不冒充文件整理後的版本已被原測試覆蓋。

若 session／配額／工具中斷，保存恢復點；下次先核對狀態及實際資料再續做，不能假裝在中斷期間持續工作。沒有可用外部排程器時，Markdown 規範本身不會自動重啟 session。

## 12. 進度與資源紀律

進度以完成的切片、已到期義務、已關閉首因、可驗證變更及剩餘阻擋表示，不以行數、hash 數、agent 次數或工作時長代替。

有重大完成、改變首因或需要外部決策時才發簡短進度；使用者不在時不要求每片回覆「繼續」。不要進入每幾分鐘輪詢相同失敗或重新啟動同一 reviewer 的忙迴圈。

依既有 runner job timeout 與工具期限執行。超時先定位工作是否實際有進度，不無限加大 timeout。費用、付費 runner、新 API 或新服務超出核准範圍就停止該項；不得為不中斷而自動升級方案。

內部 CI／review 措施不得進購票熱路徑。對 runtime 的新檢查按 v1.5 比對必要性、能否融合既有 browser operation、是否新增排程 hop／CDP／檔案 I/O。速度改善以相同條件量測，不靠放寬正確性或提高站點請求頻率。

## 13. uTiki P2→P8 的特殊門檻

下表是執行導引；完整義務仍以已核准 v1.5 §19 與 catalog 為準。

| 階段 | 可自主推進的前提／內容 | 不得越過的界線 |
|---|---|---|
| P1 收尾 | 依既有權限完成修正、差異覆核與正式 aggregate | 未實際出站不可標 P2 已開始正式實作 |
| P2 | 前階段通過；新模型／policy／ports 與完整型別／契約測試 | 不新增未核准產品能力 |
| P3a | JS 外部化與必要 resource／spec／source/frozen 同期驗證 | 目標平台不足保留 BLOCKED，不把 build 延到 P8 |
| P3b | 批次操作與 readiness；正確性及成本一起驗 | 不用兩套 fast engine 或省略 live audit |
| P4 | Session arbiter、Purchase／Input 轉移；隔離 harness | 不在同一 tab 同時派發新舊引擎 |
| P5 | Refresh／核心入口／生命週期整合，保留 coordinator 契約 | 不放寬間隔、lease 或未知結果保護 |
| P6a | 候選只有新 owner；source/frozen upgrader 與全離線驗收 | 只能 READY_FOR_LIVE；不得自動進 P6c |
| P6b | 只有維護者已提供明確真站範圍、帳號、停止點等授權才執行 | 使用者休息、泛稱「做到 P8」不等於真站與 final-delete 核准 |
| P6c | P6b 證據及候選對應的 final-delete 核准實際成立後 | 本規範本身不授權最後刪除 legacy |
| P7 | 依原前置及授權做端到端量測、碰撞／上游演練 | 改 runtime 後適用真站門檻仍要重驗 |
| P8 | 完整最終 target／證據及適用真站驗證，另有發布決策 | 未核准 RELEASE_BLOCKED，不發 tag／release／部署 |

沒有真站／刪除／發布核准時，仍可做原計劃明確容許、且不依賴受阻步驟的離線準備；要標為準備而非正式完成。不能以此在同一候選提前做 P6c 刪除，或自行把 live 改成可選。

## 14. 這幾輪 P1 經驗的具體裁決例

| 事件 | 正確自主選擇 | 不應再做的事 |
|---|---|---|
| 51 個 Windows 測試失敗 | 按首因分群，先修路徑與 Python 啟動鏈，再看殘餘 | 51 個各寫一套例外或直接 skip Windows |
| Windows .py runner 改了，validator 仍要求 x bit | 同步整條直接契約，保留必要輸入核對 | 只補 chmod 或放寬所有可執行檔檢查 |
| Artifact 複本失去執行位元 | 依 Python 腳本實際啟動語意消除多餘 mode 前提，補傳遞回歸 | 為維持多餘前提重建通用 artifact 系統 |
| producer 綠，aggregate 首次失敗 | 讀首個實際失敗，驗真正傳遞邊界 | 宣稱 63/63 已足以出站 |
| catalog bytes 未變，新修正只改 launcher | 沿用原內容核准，覆核程式差異 | 每更新 candidate SHA 就重開 catalog 全量核准 |
| harness 要乾淨 HEAD | 在授權分支 checkpoint 後測 exact SHA | 不准 commit 又要求乾淨；或測舊 HEAD 冒充工作樹 |
| reviewer 暫不可用 | 保留待覆核，做前置已成立的獨立工作 | 自審冒充、無限重啟 subagents、整個專案無謂忙等 |
| 原有測試預期被前置錯誤遮蔽 | 用合法對照和指定差異驗因果 | 只改 expected message 或補假的 report |

本規範的成效是代理能在授權內「完成、驗證、收斂、接續」，不是規則愈多愈好。已有事實顯示規範不足時提出窄幅修訂；不得由代理自行修改本規範來解除當前 blocker。
