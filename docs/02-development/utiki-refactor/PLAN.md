# uTiki 重構計畫

本計畫處理中信兄弟與味全龍共用的 uTiki 購票流程。目標是在保留現有使用者行為與安全邊界的前提下，讓程式容易修改、擴充與驗證，並減少不必要的等待。日常進度見 [STATUS.md](STATUS.md)；實際驗證命令與分級見 [測試執行指南](../testing_execution_guide.md)。

## 範圍與完成條件

- 交付 Windows x64 與 macOS arm64 的原始碼執行路徑及既有設定網頁。其他平台、帳號資料、Cookie、browser profile 與共用刷新資料維持原有語意。
- uTiki 行為設定只接受一份 current 格式；使用者可手動重新填寫。不建立舊值升級器、執行期 fallback 或雙寫。
- 不新增自動付款，也不為了速度提高站點請求頻率或削弱既有限流。真站驗收由使用者之後手動執行；離線完成時明確標記 `LIVE_NOT_VERIFIED`。
- 完成時，正式主入口使用新 owner；舊 workflow、相容 facade 與不用的狀態只在其責任已接替並通過離線驗收後移除。不能以新增檔案或測試數量當作切換完成。
- 本次不交付 uTiki 的 PyInstaller 成品、安裝包、發布流程或產品設定升級器。

## 重構原則

1. **一個 session owner。** 每個 tab 的購票、導覽與刷新只有一個可授權副作用的 owner。背景工作只回報帶有來源身分的結果；同一 tab 不同時由新舊引擎點擊、提交或重新載入。
2. **決策與瀏覽器操作分開。** 純規則處理選擇與狀態轉移；application 協調事件與授權；具體 browser adapter 執行 DOM/CDP。只有實際需要的能力才建立 port，不先造跨平台通用框架。
3. **副作用以結果證據推進。** 點擊、填值、reload 或 submit 的指令返回，均不直接等於網站接受。提交結果未知時停止自動重送；晚到結果仍歸屬原操作。CAPTCHA、登入、彈窗與 429 恢復保留各自的安全出口。
4. **速度以量測改善。** Ready 後立即接續，移除沒有用途的固定等待與重複 CDP；保留送出前必要的即時核對與共用刷新節流。分開量測本機決策、瀏覽器往返與網站等待。
5. **保護既有功能。** 先固定目前有效行為，再以可回復的完整流程切片搬移。重構中發現原本的 bug，可在受影響切片明確修正與測試；不要以「保持舊行為」延續已證實的錯誤。

## 目標責任

```text
主迴圈與設定入口
        │
        ▼
uTiki bootstrap ── 注入現有核心服務與 browser 能力
        │
        ▼
session controller ── 唯一狀態與副作用授權
        │
        ├── domain：頁面辨識、選擇、購票／輸入／刷新轉移
        └── adapters：DOM/CDP、腳本、coordinator、通知
```

主迴圈只決定路由、提供控制狀態並接收結果。Domain 不依賴 browser、設定 UI 或 I/O。既有跨程序 SQLite 刷新協調器繼續處理間隔、租約與 429；新的 session controller 只管理它與購票操作的先後關係。通知不阻塞熱路徑，且「嘗試傳送」與「已送達」分別記錄。

## 必須保留的行為

| 流程 | 驗收重點 |
|---|---|
| 日期與區域 | 同一文件的候選只採取一次可歸屬操作；按鈕確實可操作，導頁或會員驗證結果需回讀。 |
| 票數與座位 | keyword、票種、座位模式與可售狀態遵守現行設定；舊 tuple／dict 邊界逐步換成具名資料。 |
| 輸入、CAPTCHA、提交 | 填值失敗禁止提交；人工處理與晚到結果有明確歸屬；未知提交不重送、不被刷新覆蓋。 |
| 刷新、429 與暫停 | 保留跨程序節流、cooldown、租約清理與 pause/stop；不因新控制器多發 reload。 |
| 設定 | UI、預設值、載入、儲存與 hot reload 使用同一 current uTiki 格式；其他平台與 accounts 值不受損。 |
| 資源與效能 | production 腳本從模組相對位置載入；Windows／macOS 路徑可用；無理由的固定等待或重複往返須量測並處理。 |

另存的職棒工作稿只作為候選來源；有需求且符合安全與效能驗收的部分，才逐項移植。分支位置見 [STATUS.md](STATUS.md)。

## 施工順序

每一項以可執行的流程與測試結束。

1. **固定基線。** 列出正式 caller、設定、跨程序刷新與外部副作用；保留能重現目前行為的純邏輯、DOM fixture 與整合測試。記錄現有 CI 失敗與可運行命令，分清既有工具故障和產品故障。取得相同條件下的延遲基線。
2. **接通一條完整離線流程。** 由 bootstrap 到 session controller，在隔離 fixture 走日期、區域與票數／座位；browser adapter 使用 production script。舊 owner 在正式執行期仍唯一，隔離測試不造成第二個實際副作用來源。
3. **補齊購票與恢復。** 加入輸入、CAPTCHA、提交、彈窗、登入、未知結果、停止與晚到結果。以少量有代表性的事件序列測試重複提交與跨操作衝突。
4. **切換正式路徑。** 將刷新控制、主迴圈及 current 設定 UI 接到新 owner；在同一可回復變更單位移除雙寫與執行期 fallback。驗證其他平台設定和帳號資料未改變。
5. **清理與收斂。** 查完 caller 後移除已接替的舊 workflow／facade／測試橋接。檢查 Windows 與 macOS 原始碼啟動、隔離瀏覽器流程與效能回歸；彙整已測和待手動真站範圍。

第 2–4 項可以依頁型拆成更小的實作提交，但每個交付點都必須說明實際接通的輸入、動作、結果與測試。遇到新證據可調整施工順序，只更新本計畫的有效決策與 [STATUS.md](STATUS.md)，不建立版本差異文件。

## 驗證與完成判定

- 日常修改先跑受影響 pytest、修改過的 Python 語法與適用的型別／靜態檢查；文件修改確認連結和命令。共用服務變動擴大到受影響 caller。
- 完整流程切片與正式入口切換時，跑完整 pytest、型別檢查、production script 瀏覽器 fixture、網路隔離、設定與資源回歸，以及實際 CI。測試環境不可連到真售票網站或使用私人 profile。
- 效能比較採同環境、同頁面與同設定；記錄中位數／高分位、CDP 次數、額外等待與安全限制。微小波動不作為任意改架構的理由。
- 正式路由只呼叫新 owner、舊副作用路徑不再可達、設定只讀寫 current 格式、其他平台保持通過，才可宣告離線重構完成。真站未驗證及其待辦須清楚列出。
- 現有 v1.6 catalog／P1／P2 gate 暫時保留為舊工具；替代的聚焦測試與常規 CI 可驗證後，再一次性退役舊 gate，並移除它們所依賴的 `catalog-approval-v1.6.md` 與 `core-integration-inventory.md`。移除前將仍有效的核心接合約束放入現行程式碼邊界或測試。舊 gate 的歷史 PASS 不等於新版本通過；目前已知失敗也不能隱藏。

具體命令、測試層級與結果說法由 [測試執行指南](../testing_execution_guide.md) 維護。
