# 工程審查指南

**文件說明**：定義 Tickets Hunter 程式碼與架構變更的審查重點、嚴重度與交付格式。

**最後更新**：2026-10-25

協作規則見 [AGENTS.md](../../AGENTS.md)，驗證命令見[測試指南](testing_execution_guide.md)，模組責任見[程式碼邊界](code-boundaries.md)。使用者泛稱「審查」或要求全面、架構審查時，預設檢視適用的功能、狀態與副作用、架構、擴充性、測試及文件；明確限定範圍時依指定範圍審查，交代未涵蓋處。下列面向依實際變更、現行 caller 與當次需求判斷適用性；uTiki 的行為與相容要求以目前程式、相應測試及當次需求為依據，不從通用清單新增購票資格、遷移、打包或真站驗收門檻。

## 1. 審查目標

工程審查要找出會造成錯誤選票、重複送出、無限刷新、敏感資料洩漏或無法回復的問題，也要檢查責任歸屬、正式流程接線與新增租戶時的維護成本。架構 finding 應指出具體 caller 或擴充情境、必須改動的位置及錯誤或維護後果；不以個人風格、檔案長度或抽象層數本身定罪。

審查採 findings-first：先依嚴重度列出有證據支持的問題，再提供範圍、整體摘要與測試缺口。行為缺陷應盡量重現；架構問題可由具體變更情境與 caller 證據支持。沒有 finding 時也要明確說明審查界線與剩餘風險。

## 2. 嚴重度

| 等級 | 定義 | 例子 |
|------|------|------|
| P0 | 會造成嚴重法律、安全或不可逆損害，必須立即停止 | 自動付款、洩漏 Cookie、任意程式執行 |
| P1 | 可信的觸發條件下會造成重大錯誤、重複副作用或卡死；影響本輪交付時須先處理 | 選錯區域、重複送單、彈窗後永久停住、刷新風暴 |
| P2 | 特定條件下的正確性或有具體成本的維護問題 | 多分頁狀態互相污染、測試假綠、current 設定與正式入口不一致 |
| P3 | 低風險但具體可改善的品質問題 | 誤導命名、過時文件、重複但未造成行為分歧的程式碼 |

嚴重度依影響、可達前提、可恢復性與證據評估；罕見但後果重大的情境不能只因少見而降級。finding 必須包含位置、觸發條件或具體擴充情境、實際後果及建議修正方向。不要只寫「可能有問題」或泛泛而談最佳實務。

分級不等於延期或擴張授權。本輪範圍內已確認的問題應修正並重審；使用者明確排除的範圍記下位置、風險及排除依據，不在本輪改動；證據不足時列出所需證據與查證方式，不宣稱已確認技術債。若跨範圍問題有嚴重即時風險，先向使用者說明並請其決定範圍。

## 3. 審查面向

全面審查逐項判斷下列面向是否適用；局部變更審查按影響選取，無關項目不因此變成新功能或施工要求。

### 3.1 需求與適用計畫

- 修改是否對應當次需求、實際 caller、適用計畫與明確驗收條件；公開 PR 的 Issue 流程另見 [CONTRIBUTING.md](../../CONTRIBUTING.md)。
- 十二階段是否只作通用功能分類，沒有取代該平台現行流程順序與能力邊界。
- 新功能是否只改必要階段，沒有順便改變其他平台的行為。
- 到達 checkout 後是否只通知，不包含自動付款。

### 3.2 平台與依賴邊界

- 平台是否保持在 `src/platforms/`，沒有反向匯入或跨平台 import。
- 共用邏輯是否真的跨平台；平台 selector、URL 與業務規則不得塞進 `util.py`。
- 家族平台共用必須基於已驗證的 page contract，不能只因 UI 相似就共用實作。
- 共用流程、租戶能力與個別站點規則是否各有明確 owner；避免「中信，否則味全」一類隱式 fallback，或讓新租戶默認取得某站專屬能力。
- 以具體新增租戶情境盤點要修改的 Python profile／auth、正式路由、設定 UI 與測試；區分必要的跨層接線、同一語義的重複權威及會造成行為分歧的平行規則。不同執行邊界不必硬塞成單一檔案，但須有可核對的契約。
- 狀態、設定預設值及副作用是否有清楚 owner；新 helper 是否只多一層轉送、建立平行狀態或繞過正式入口。長度與複雜度數值只作定位線索，拆分仍以責任及行為邊界判斷。
- 新 module/package 是否按實際用途接入正式 source caller；uTiki 涉及設定時使用 current 格式。只有交付範圍包含打包時才檢查 PyInstaller hidden imports。

### 3.3 URL、頁面與輸入安全

- URL host、path、query 與頁型是否明確驗證；未知頁面是否 fail closed。
- 重新導向後是否重新判斷 host 與頁型。
- fast navigation 是否先建立 pending state，僅接受允許的 structured action，並在目的頁核對 route/query 與 hidden identifiers；`SendA` 等需原生處理的 action 不得直達。
- DOM 元素是否有穩定身分；同名、空文字、重複 id 與 re-render 是否安全。
- 注入 JavaScript 是否使用 IIFE 與 `json.dumps()`，且不污染 `window`。
- 外部回應、設定與 DOM 資料是否避免動態求值及 shell 注入。

### 3.4 選擇、填值與送出

- 關鍵字包含、完全符合、AND、OR、排除與 fallback 語意是否維持。
- stable identity 與 volatile availability 是否按現行支援頁型分開；已使用的 table row、map title、action status 來源沿現行核對條件處理，不因本指南新增必備來源。
- observe 與 commit 之間是否重新確認 URL、document、候選身分與可售狀態。
- 票數、座位與 checkbox 寫入後是否按現行分支核對；submit 前保留既有 payload 與 document 核對，不能把指令回傳當成網站接受。
- 短間隔或重複 tick 是否仍只產生一次 click、submit 或通知。

### 3.5 狀態生命週期

- 狀態是否依分頁／document 隔離，導頁、重新整理、登入切換後是否正確失效。
- purchase identity 與結果歸屬是否保留現行 tenant、performance、group、price-area／mode 等既有欄位與時點；不從本指南新增指定 session／Cookie 資格。
- document 改變時是否先 reduce／attest fast navigation、submit awaiting、conflict 與 reload probe 等跨 document transition，再清除 source-document state。
- `pending`、`committed`、`failed` 是否有明確轉換；失敗不應被誤標為成功。
- CAPTCHA、送出、dialog 與刷新狀態是否可恢復，不會殘留到下一輪。
- 熱重載設定後，哪些狀態保留、哪些重設是否有定義。

### 3.6 彈窗與錯誤恢復

- 彈窗是否先讀取可驗證文字／角色，再分類；未知彈窗不得自動當成座位衝突。
- 成功加入購物車、座位衝突、超出額度、登入失效、CAPTCHA 錯誤與未知錯誤是否有不同處理。
- submit 前是否二次檢查 dialog；click 後是否進入 awaiting-result，容許延遲 dialog／導頁而不重送。
- committer 是否只回報 dispatched；awaiting-result 是否有明確期限，無導頁、已知 dialog 或可驗證 evidence 時是否進入 sticky unknown terminal，而非永久等待或自動重送。
- blocker 是否在 dismiss 前保存；dismiss 後是否驗證彈窗真的關閉，失敗時是否仍禁止其他副作用。
- recovery 是否依現行頁型與拒絕種類處理：已知 CAPTCHA 拒絕保留同頁清欄、換圖及新圖片觀察條件；座位／票數衝突以新 document 為重新準備條件。只有現行選位頁、無自動提交的人工送出分支，在健康、身份及清空條件全部核對通過時，才可接受網站已換好的新 document 並省略本程式重複 reload；其他分支沿既有刷新保護 reload 並等待新 document。不得把兩者合成通用重試出口，未知送出結果也不得自動重送。

### 3.7 刷新與限流

- 同一 tab 的刷新是否由現行 owner 仲裁；共用協調器啟用時經現行協調路徑，停用時保留現行本地間隔，兩者都不旁路既有保護。
- 429、一般缺票與未知網路錯誤是否分開；單一分頁的未知狀態不能誤觸發全域 429。
- 重新整理是否具備 reservation／commit 邊界，避免多個 tick 或程序同時刷新。
- pause 是否釋放 reservation／probe lease但保留 recovery intent；resume 是否仍遵守剩餘間隔與 cooldown。
- same-URL reload 是否通知外層重新執行 Cloudflare／document gate；coordinator disabled 時是否仍只由 family refresh controller 刷新。
- 測試或 fallback 不得繞過設定間隔。

### 3.8 登入、隱私與記錄

- 登入是否使用使用者既有合法 Cookie／profile，不把秘密複製到設定以外的位置。
- auth 是否沿現行租戶、登入欄位與 session 狀態判斷；不以通用審查文字新增購票前的 Cookie 資格。
- debug、例外與測試 fixture 是否已脫敏。
- Issue、PR、截圖與測試記錄是否可能暴露帳號或訂單資訊。

### 3.9 測試可信度

- 測試是否驗證行為，而不只是檢查 production script 字串包含某個 marker。
- fake 是否依操作語意回應，並驗證呼叫順序、參數與副作用次數。
- mock 是否 patch 真正查找依賴的 owner；新增案例是否走到正式 caller 及目標分支，而非把整個判斷預先 mock 成預期結果。
- 模組 `_state`、時間、亂數、檔案與網路是否隔離。
- DOM 改動是否有符合頁型契約的合成／已脫敏 fixture，並依適用計畫完成必要的瀏覽器驗證。
- 測試數量與通過宣稱是否可由命令輸出核對。

### 3.10 文件與發行

- 功能是否接通適用的設定預設值、讀取／儲存／熱更新、正式 caller、執行與結果回饋；若只完成部分接線，須如實標明。
- 設定名稱、預設值、UI 與當次範圍內確有要求的相容或遷移是否同步；不從通用清單要求 uTiki 舊設定升級。
- 架構、測試與使用者文件是否描述目前行為，而非預定行為。
- 新 import、資料檔或 package 是否能由正式 source caller 載入；只有打包屬交付範圍時才檢查 PyInstaller 收錄。
- Windows cp950 下 `.py` 是否沒有 emoji 或不相容輸出。

## 4. 建議審查順序

1. 讀當次需求、適用計畫與驗收條件；公開 PR 再對照 Issue。
2. 檢查 diff 範圍及既有未提交變更。
3. 從公開入口追蹤到副作用，確認狀態與錯誤路徑。
4. 檢查責任與依賴方向，選一個與本次變更有關的擴充情境，辨認必要接線與意外的平行規則。
5. 對照測試，找出只有實作沒有覆蓋、或只有字串 fake 的區域。
6. 執行與風險相稱的驗證；命令見 [測試執行指南](testing_execution_guide.md)。
7. 依 P0 → P3 輸出 findings，交代已修、明確排除與待查證項目，最後寫摘要與剩餘風險。

## 5. 審查輸出格式

```text
Findings

- [P1] 短標題 — path/to/file.py，函式名稱
  觸發條件或具體擴充情境、證據、目前行為、實際後果，以及修正方向。

Scope / disposition

- 審查了哪些入口、依賴、狀態與文件；哪些範圍未涵蓋。
- 發現事項分別標示本輪已修、使用者明確排除，或尚待查證（不得寫成已確認）；部分接線不得稱為完整功能。

Open questions / assumptions

- 尚未取得哪一種頁面或行為證據。

Validation

- 實際執行的命令與結果。
- 未執行的驗證及原因。

Summary

- 變更目的、架構與擴充性判斷、完整／部分／未接通的功能狀態；沒有 finding 時，寫明「在上述範圍未發現阻擋問題」，不推論全專案沒有技術債。
```

行號可用於當次 inline review；長期 Issue 與設計文件請以檔案加函式／符號名稱描述，避免日後失效。

## 6. 大規模重構檢查項目

大規模重構依當次需求、實際 caller 與驗證範圍確認。以下是需要時選用的檢查項目，不自行設定批准或真站 gate；已完成的 uTiki 重構紀錄見[封存計畫](archive/utiki-refactor/PLAN.md)。

- 有明確的目標、施工界線與各批次驗收。
- characterization tests 先於行為搬移。
- 舊、新實作不會同時執行相同副作用；需要比較時只允許 shadow decision。
- facade 與舊實作移除、設定及交付範圍依當次需求與實際 caller 處理；uTiki 目前只讀 current 行為設定，其他相容、打包或跨平台工作不由歷史重構計畫永久限定。
- 各批次可辨識、可驗收且可恢復；是否合併、部署或發布依使用者當次授權。
- 真站驗證只回報實際執行範圍；未執行時照實列為未驗證，是否需要執行由當次工作與授權決定。

## 7. 接收原作者更新的審查

本 fork 會依使用者需求接收原作者更新，保留自有職棒售票能力；接收更新不以向原作者建立 Issue 或 PR 為前提。先分清任務是「取得並評估更新」還是「將更新接入本分支」。只做 fetch 與差異審查時，不宣稱已整合，也不因此執行產品驗證。

1. **確認來源與工作狀態**：核對 repository、分支、HEAD、工作樹與暫存區、遠端的 fetch URL、要審查的原作者目標 SHA。保留未提交及未追蹤檔案，不以 reset、clean 或整批 restore 清空；不使用未審查的 `git pull` 直接接入。記下已整合的上游基點與過去選擇性移植的來源 SHA；最後 fetch 到的 SHA 不等於最後已整合的 SHA。來源脈絡不明時先標為待查證。
2. **比較雙邊變化**：由本分支與目標上游版本的共同祖先，分別檢查上游改動與 fork 改動，再加上目前未提交內容；不能只看上游最近一次 fetch 後的提交，也不能只看 Git 標出的文字衝突。對已選擇性移植的來源，比對其實際程式與測試，避免重複接入。追查檔案移動、刪除、公開入口及跨檔 caller，確認自動合併後是否有語意衝突。
3. **按影響範圍查核**：檢查上游變更是否碰到共用程式與其他平台、uTiki 正式路由與租戶能力、登入與 Cookie、設定格式與 UI、購票提交及未知結果、刷新與 429 協調、測試 fixture 與選測規則，以及依賴、build／CI 與文件。這是盤點面向；依實際差異決定深度，不把打包、真站或全部測試變成每次接收更新的固定門檻。
4. **逐項決定接法**：記錄採納、調整後採納、不採納或待查證的變更及理由，特別檢查原作者修復與本 fork 功能在同一 caller 上的交互影響。完整接入可依適用歷史合併；只接入部分時記錄來源 SHA、已取用與未取用範圍，不稱為完整同步。不要整批選 `ours`／`theirs` 或用原作者文件覆蓋 fork 規則；繼承文件維持一份現行版本，依程式現況調和內容。若更新會改變使用者行為或授權意義，先提出具體差異供使用者決定。
5. **依接入結果驗證與回報**：實際修改後依[測試指南](testing_execution_guide.md)做受影響範圍與必要整合驗證，文件變更檢查連結及 `git diff --check`；browser fixture、打包與真站驗證按變更性質及當次授權決定，不把未執行寫成通過。回報目標上游 SHA、fork HEAD、比較基點、接入方式、採納／調整／略過／待查證項目、衝突處理、實際驗證與未驗證範圍。獲准提交時，在提交說明保留選擇性接入的來源 SHA；獲准推送時核對目的 remote、push URL 與分支，不憑 remote 名稱猜測目的地。commit、push 及公開 PR 仍依使用者授權。
